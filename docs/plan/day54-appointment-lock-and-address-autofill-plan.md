# Day54 预约时段锁定与服务地址自动回填计划

日期：2026-07-15

目标模块：小程序预约下单、用户地址管理、地图逆解析、Admin 运营配置、后端订单创建校验

## 1. 背景

甲方提出两个运营侧和用户体验侧需求：

1. 预约时间需要支持平台自己锁定。例如今天 `10:00-12:00` 临时不能服务时，用户不能再预约该时段。
2. 服务地址填写时，定位当前地址不够稳定；地图选点后不能自动填入省、市、区县、街道等结构化地址。需要系统自动填写这些信息，详细地址由用户自己补充。

当前项目已经具备以下基础：

- 小程序预约页 `miniapp/src/pages/order/create.vue` 使用 `availableAppointmentSlots()` 展示固定预约时段。
- 当前固定时段定义在 `miniapp/src/utils/appointmentSlots.ts`，包括 `08:00-10:00`、`10:00-12:00`、`12:00-14:00`、`14:00-16:00`、`16:00-17:00`。
- 订单创建和价格预览接口已接收 `appointmentDate`、`appointmentTimeSlot`。
- 地址模型已包含 `provinceName`、`cityName`、`districtName`、`streetName`、`addressTitle`、`detailAddress`、`latitude`、`longitude`、`coordinateType`、`poiId`、`mapProvider`、`source` 等字段。
- 后端已有地图接口 `/api/maps/reverse-geocode` 和 `/api/maps/place-suggestions`。
- 小程序地址页已有“定位当前地址”和“地图选点”入口，但回填链路需要进一步稳定和产品化。

Day54 目标是把这两个需求补成可运营、可校验、可验收的闭环能力。

## 2. 需求一：Admin 可配置不可预约时段

### 2.1 目标

平台运营人员可以在 Admin 后台锁定某一天的一个或多个预约时段。被锁定的时段在小程序预约页不可选择，且后端在价格预览和创建订单时都必须校验，防止用户通过旧页面、缓存或接口绕过限制。

示例：

```text
2026-07-15 10:00-12:00 临时不能服务
```

配置后，小程序当天的 `10:00-12:00` 不再可预约。

### 2.2 功能范围

Admin 后台新增“不可预约时段”管理能力：

- 支持按日期锁定时段。
- 支持选择已有固定时段，例如 `10:00-12:00`。
- 支持填写锁定原因，例如“师傅排满”“临时休息”“区域不可服务”“天气原因”。
- 支持启用、停用或删除锁定记录。
- 支持查看未来若干天的锁定记录。

小程序预约页调整：

- 预约时段不再只由前端本地规则决定。
- 小程序选择日期后，应从后端获取该日期的可预约时段。
- 被锁定时段可以不展示，也可以置灰展示；首期建议不展示，降低用户误点。
- 如果某天所有时段都不可预约，显示“当天暂无可预约时段，请选择其他日期”。

后端校验调整：

- 价格预览接口需要识别不可预约时段。
- 创建订单接口必须再次校验不可预约时段。
- 如果提交时段已被锁定，返回明确错误，例如“该时段暂不可预约，请重新选择时间”。
- 锁定只影响新预约，不自动修改已创建订单。

### 2.3 建议数据模型

新增预约时段锁定表，建议命名为 `appointment_time_locks`。

核心字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `lock_date` | 锁定日期，例如 `2026-07-15` |
| `time_slot` | 锁定时段，例如 `10:00-12:00` |
| `reason` | 锁定原因 |
| `status` | 状态：`active` / `inactive` |
| `created_by` | 创建人 admin id |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

唯一约束建议：

```text
lock_date + time_slot
```

同一天同一时段只能有一条有效配置，避免重复锁定导致展示和审计混乱。

### 2.4 建议后端接口

用户侧：

```text
GET /api/appointments/slots?date=2026-07-15
```

返回示例：

```json
{
  "date": "2026-07-15",
  "items": [
    {
      "timeSlot": "08:00-10:00",
      "available": true
    },
    {
      "timeSlot": "10:00-12:00",
      "available": false,
      "reason": "该时段暂不可预约"
    }
  ]
}
```

Admin 侧：

```text
GET /api/admin/appointment-time-locks
POST /api/admin/appointment-time-locks
PUT /api/admin/appointment-time-locks/:id
DELETE /api/admin/appointment-time-locks/:id
```

首期可以只支持全平台锁定，不做服务品类、区域、师傅维度。后续如果需要再扩展 `service_id`、`district_code`、`staff_id` 等字段。

### 2.5 验收标准

1. Admin 可以新增一条 `2026-07-15 10:00-12:00` 的不可预约配置。
2. 小程序选择 `2026-07-15` 时，`10:00-12:00` 不可选择。
3. 用户停留在旧页面时，后台临时锁定该时段，用户提交订单会被后端拒绝。
4. 价格预览和创建订单对不可预约时段的判断一致。
5. 停用或删除锁定记录后，该时段重新可预约。
6. 已创建订单不因新增锁定记录被自动取消或修改。

## 3. 需求二：服务地址定位/地图选点自动结构化回填

### 3.1 目标

用户新增或编辑服务地址时，点击“定位当前地址”或“地图选点”后，系统自动解析并填入省、市、区县、街道、位置名称等结构化信息。详细地址只填写楼栋、单元、楼层、门牌号等补充信息，由用户手动完成。

### 3.2 功能范围

小程序地址页调整：

- 新增地址页进入时可以尝试定位当前地址。
- 用户点击“定位当前地址”后，获取经纬度并调用后端逆地理解析。
- 用户点击“地图选点”后，拿到选点经纬度，再调用后端逆地理解析补齐结构化字段。
- 自动回填字段：
  - `provinceName`
  - `cityName`
  - `districtName`
  - `streetName`
  - `addressTitle`
  - `latitude`
  - `longitude`
  - `coordinateType`
  - `poiId`
  - `mapProvider`
  - `source`
- `detailAddress` 不自动写入完整地图地址，只保留给用户填写楼栋、单元、门牌号等。
- 如果地图服务只返回部分字段，则只回填已返回字段，缺失字段允许用户手动补充。
- 如果用户手动修改了省、市、区县、街道、位置名称或详细地址，应提示地址文字已修改，并清除旧坐标或要求重新定位，避免地址文字和坐标不一致。

后端地图接口调整：

- `/api/maps/reverse-geocode` 应稳定返回省、市、区县、街道、门牌号、推荐地址、POI 列表。
- 腾讯地图和高德地图 provider 的返回字段需要统一成当前项目地址模型可直接消费的结构。
- 地图接口失败时返回明确错误，前端提示用户可继续手动填写。

### 3.3 推荐交互

定位当前地址：

```text
用户点击“定位当前地址”
-> 微信定位授权
-> 获取经纬度
-> 调用 /api/maps/reverse-geocode
-> 自动填入省、市、区县、街道、位置名称
-> 用户补充详细地址
-> 保存地址
```

地图选点：

```text
用户点击“地图选点”
-> 打开微信地图选点
-> 用户选择 POI 或地图点
-> 返回经纬度和选点名称
-> 调用 /api/maps/reverse-geocode
-> 自动填入省、市、区县、街道、位置名称
-> 用户补充详细地址
-> 保存地址
```

定位失败：

```text
定位未授权 / 地图接口失败
-> 给出明确提示
-> 保留手动填写入口
-> 不阻止用户保存纯手动地址
```

### 3.4 验收标准

1. 用户点击“定位当前地址”后，地址页能自动填入省、市、区县、街道和位置名称。
2. 用户点击“地图选点”并选择位置后，返回地址页能自动填入结构化地址字段。
3. 详细地址字段不被整段地图地址覆盖，只由用户填写楼栋、单元、楼层、门牌号等信息。
4. 保存地址后，订单创建时继续生成 Day48 订单地址快照。
5. Admin 订单详情和师傅端订单详情继续展示完整地址。
6. 有经纬度的订单，师傅端可以继续打开地图导航。
7. 定位未授权、地图接口失败、逆解析缺字段时，前端有明确提示，并允许用户手动填写保存。

## 4. 实施顺序

1. 后端新增预约时段锁定数据模型、迁移和基础 service。
2. 后端新增用户侧可预约时段接口，并把价格预览、创建订单接入同一套时段可用性校验。
3. Admin 新增不可预约时段管理页面。
4. 小程序预约页改为读取后端可预约时段，替换纯前端本地时段判断。
5. 梳理地图逆解析返回结构，统一 Tencent/Amap provider 输出。
6. 小程序地址页改造定位当前地址和地图选点后的自动回填逻辑。
7. 补充后端接口测试和小程序真机验收。

## 5. 非目标

Day54 首期不做以下内容：

- 不做按师傅个人排班锁定。
- 不做按区域、服务品类、门店的复杂容量管理。
- 不自动取消或改约已有订单。
- 不实现用户端改约流程。
- 不把详细地址完全交给地图自动填写。
- 不强制用户必须授权定位；用户仍可手动填写地址。

## 6. 风险与注意事项

1. 不可预约时段必须以后端校验为准，前端隐藏或置灰只是体验优化。
2. 价格预览和创建订单必须共用同一套时段可用性判断，避免用户看到可提交但最终失败。
3. 地址自动回填不能覆盖用户手动填写的详细地址，否则容易造成门牌号丢失。
4. 地图逆解析返回的街道、POI、推荐地址在不同 provider 下字段不完全一致，需要在后端 provider 层统一。
5. 用户修改地址文字后，如果继续保留旧坐标，会影响师傅导航，必须提示重新定位或清除旧坐标。
