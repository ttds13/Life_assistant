# Day51 小程序首页会员卡与 0 元权益预约前端改造计划

更新时间：2026-07-15  
前置依赖：Day48 订单地址强关联、Day49 会员卡分钟核销闭环、Day50 商品购买/服务预约/用户权益卡命名与读模型均已上线。  
目标：将小程序首页“更多服务”改造成会员卡商品入口，修复购卡成功后的立即预约跳转，并保证从用户权益卡发起的预约始终以会员卡权益模式进入预约页、展示应付 0 元并提交正确的权益核销参数。

> Day51 以小程序前端流程改造为主，同时补齐价格预览的最小服务端契约。页面不得仅把金额文字改成 0 元；最终提交必须携带用户权益卡 ID 和核销分钟，并由服务端校验卡归属、状态、适用服务、余额和核销规则。Day51 不新增数据库表或字段，不改变 Day49 的冻结、核销、释放、激活和到期状态机。

## 1. 统一业务命名

Day51 继续使用 Day50 已确定的业务名称，避免把商品、用户资产和一次服务预约都简称为“会员卡订单”。

| 场景 | 统一名称 | 含义 |
| --- | --- | --- |
| 首页展示和待购买内容 | 会员卡商品 | Admin 配置的可售会员卡模板版本 |
| 支付成功后发放给用户的卡 | 用户权益卡 | 具有状态、余额、激活期限和有效期的用户资产 |
| 使用用户权益卡产生的预约 | 会员卡权益预约 | 冻结并最终核销用户权益卡分钟的服务预约 |
| 直接购买服务产生的预约 | 服务权益预约 | 普通现金服务订单对应的一次服务预约 |

涉及 ID 时必须明确语义：

```text
shopCardId / cardTemplateId  = 会员卡商品模板 ID
memberCardId                 = 用户权益卡 ID（UserMemberCard.id）
serviceId / serviceCode      = 本次要预约的服务
memberCardConsumeMinutes     = 本次计划冻结/核销分钟
purchaseOrderId              = 会员卡商品购买订单 ID
```

禁止把会员卡商品模板 ID 作为 `memberCardId` 提交预约。

## 2. 当前问题与原因

### 2.1 首页仍在展示服务分类

当前 `miniapp/src/pages/home/index.vue` 的“更多服务”读取 `serviceCategories`，卡片只展示分类名称并进入普通服务列表。它没有加载可售会员卡，也不能展示会员卡价格、总权益、激活期限和有效期。

### 2.2 购卡成功后“立即预约”没有预约上下文

当前 `miniapp/src/pages/payment/result.vue` 在会员卡商品支付成功后弹出预约提示，但点击“立即预约”执行的是：

```text
switchTab('/pages/home/index')
```

该跳转没有携带 `purchaseOrderId`、新发放的 `memberCardId`、适用服务和核销分钟，因此只是回到首页，并未开始会员卡权益预约。

微信支付完成回调与服务端支付通知还存在短暂时序差。前端收到支付控件成功并不等于用户权益卡已经可查询，不能在尚未取得 `grantedUserMemberCardId` 时直接弹出可预约提示，也不能把仍为待支付的订单强行显示成支付成功。

### 2.3 用户权益卡预约仍经过普通服务详情

当前 `miniapp/src/pages/card/index.vue` 的“去预约”在只有一个适用服务时进入普通服务详情；多个服务时进入服务列表，选择后仍进入普通服务详情。普通服务详情固定展示 `service.basePrice` 和普通“起步价”，所以会员卡权益预约会先看到“2 小时 99 元”等现金商品信息。

### 2.4 预约页只把合计临时改为 0

当前 `miniapp/src/pages/order/create.vue` 存在四个风险：

1. 服务信息区域固定展示 `service.basePrice`，没有区分现金预约和会员卡权益预约。
2. `/orders/price-preview` 不接收 `memberCardId` 和 `memberCardConsumeMinutes`，返回的仍是普通服务价格明细。
3. 前端仅通过 `selectedMemberCard ? 0 : payableAmount` 把底部合计改成 0，金额明细仍是普通服务价格，服务端也没有在预览阶段确认该卡可用。
4. 如果路由指定的用户权益卡加载失败或不适用于当前服务，页面会清空选卡状态并退回现金下单模式，用户可能在不知情时提交 99 元现金订单。

Day51 必须修复整个预约意图链路，不能只替换一个金额组件。

## 3. 目标用户流程

### 3.1 从首页购买会员卡商品

```text
首页
-> 会员卡商品区
-> 点击某张会员卡商品
-> 卡包购买区定位该商品并展示完整规则
-> 创建会员卡商品购买订单
-> 微信支付
-> 服务端支付确认并发放用户权益卡
-> 询问是否立即预约
```

### 3.2 购卡后立即预约

```text
支付成功
-> 根据 purchaseOrderId 查询订单详情
-> 等待 status=completed 且取得 grantedUserMemberCardId
-> 加载这张用户权益卡及其适用服务
-> 单一适用服务：直接进入预约页
-> 多个适用服务：进入仅包含该卡适用服务的选择页
-> 选择后直接进入预约页
-> 选择地址、时间和核销分钟
-> 服务端返回会员卡权益价格预览
-> 应付 0 元并提交预约
-> 冻结对应分钟，生成师傅可见服务任务
```

### 3.3 从卡包使用已有用户权益卡

流程与购卡后立即预约共用同一导航方法：

```text
卡包 -> 用户权益卡“去预约”
-> 解析适用服务
-> 单服务直接进入预约页 / 多服务先选服务
-> 会员卡权益预约（0 元）
```

卡包和支付结果页不得分别维护两套不同的卡适用服务和跳转判断。

## 4. 首页“会员卡”区域

### 4.1 数据源

`miniapp/src/pages/home/index.vue` 新增加载：

```text
GET /api/member-cards/shop
```

复用 `getPurchasableMemberCards()` 和 `PurchasableMemberCard`，只展示 `status=1` 的可售会员卡商品。首页服务、Banner 和会员卡商品采用独立容错；某一个接口失败不能让其他区域全部进入错误页。

首页不再为“更多服务”加载或渲染服务分类。服务分类能力继续保留在搜索和服务列表页，不删除服务分类接口。

### 4.2 页面结构

将首页“更多服务”替换为“会员卡”，列表至少展示：

```text
会员卡名称
售价
总权益分钟
购买后激活期限（N 天内激活）
激活后有效期（N 天）
适用服务摘要
查看/购买入口
```

展示规则：

1. 权益统一以分钟为底层口径；如产品需要显示“次”，同时展示 `unitMinutes` 和换算说明，不能只显示次数而隐藏分钟规则。
2. `activationDeadlineDays` 为空时显示“购买后首次使用激活”，有值时显示“购买后 N 天内激活”。
3. `validityDays` 显示为“激活后 N 天有效”；不在前端自行计算固定到期日期。
4. 适用服务优先读取结构化 `serviceRuleList`，旧 `applicableServices` 只作兼容展示，前端不自行猜测服务规则。
5. 首页默认展示有限数量，并提供进入卡包购买区查看全部的入口；空数据时该区域显示“暂无可售会员卡”，不把整页判定为“暂无服务”。

### 4.3 点击行为

首页点击会员卡商品进入现有卡包购买页，并携带商品定位参数：

```text
/pages/card/index
?shopCardId=<会员卡商品模板ID>
&source=home_member_card
```

卡包页在商品列表加载完成后滚动或定位到对应商品，突出当前商品，并展示购买按钮。若 `shopCardId` 已下架或不存在，显示明确提示并保留其他可售商品，不能误定位到第一张卡。

本阶段不在首页直接调起支付，避免用户未阅读激活期限、有效期、核销分钟和适用服务就创建购买订单。

## 5. 统一会员卡权益预约路由

### 5.1 最终预约路由契约

进入预约页的统一路由为：

```text
/pages/order/create
?serviceId=<serviceId>
&serviceCode=<serviceCode>
&memberCardId=<用户权益卡ID>
&memberCardConsumeMinutes=<可选核销分钟>
&source=member_card
```

规则：

1. `memberCardId` 必须是 `UserMemberCard.id`。
2. `memberCardConsumeMinutes` 可以不传；预约页加载该卡对当前服务的有效规则后选择默认合法分钟。传入时也必须重新校验是否属于 `allowedMinutes`。
3. `source=member_card` 表示明确的会员卡权益预约意图。该模式下卡加载失败时必须阻止提交，不得静默降级为现金服务订单。
4. 路由中的名称、价格、余额只可用于首屏占位，不作为创建订单的可信数据。

### 5.2 单一适用服务

当用户权益卡当前只有一个可预约服务时，从卡包或支付结果页直接进入 `/pages/order/create`，不再进入 `/pages/service/detail`。

### 5.3 多个适用服务

当存在多个可预约服务时，先进入：

```text
/pages/service/list
?memberCardId=<用户权益卡ID>
&cardType=<cardType>
&serviceCodes=<服务代码集合>
&source=member_card
```

服务列表进入会员卡模式后：

1. 标题显示“选择预约服务”。
2. 只展示服务端确认适用于该卡的服务。
3. 点击服务直接进入 `/pages/order/create`，不再进入普通服务详情页。
4. 必须继续携带 `memberCardId` 和 `source=member_card`。
5. 如果没有适用服务，展示“该会员卡暂时没有可预约服务”，不得回退到全量普通服务列表。

普通服务浏览流程仍可继续经过 `/pages/service/detail`，两种模式按 `source` 明确分开。

### 5.4 共享导航能力

新增小程序内部共享方法，例如：

```text
miniapp/src/utils/memberCardReservation.ts
```

职责仅包括：

1. 校验用户权益卡是否可用且有余额。
2. 读取结构化适用服务规则并请求服务端服务列表。
3. 决定单服务直达预约页或多服务进入选择页。
4. 统一编码路由参数和来源。

卡包页与支付结果页必须复用该方法，避免再次出现入口行为不一致。

## 6. 购卡成功后的立即预约

### 6.1 以服务端订单详情为准

`miniapp/src/pages/payment/result.vue` 在会员卡商品支付后必须调用 `getOrderDetail(orderId)`，并同时满足以下条件才弹出“是否立即预约”：

```text
order.orderType === 'member_card_purchase'
order.status === 'completed'
order.memberCardPurchase.grantedUserMemberCardId > 0
```

不能只依赖页面 query 中的 `status=success`，也不能在 `requestPayment` 返回后直接假设发卡完成。

### 6.2 支付通知时序

支付控件成功后进行有限次数、带间隔的订单状态刷新：

```text
支付控件成功
-> 查询订单详情
-> 未完成或尚未发卡：显示“权益发放中”并继续有限重试
-> 完成且已发卡：展示购卡成功并允许立即预约
-> 超时：展示“支付结果确认中”，保留“刷新结果”和“查看订单”入口
```

禁止在刷新后无条件执行 `status='success'`。页面销毁时清理定时器，避免重复弹窗和后台请求。

### 6.3 弹窗按钮

| 按钮 | 行为 |
| --- | --- |
| 立即预约 | 使用 `grantedUserMemberCardId` 调用统一会员卡预约导航 |
| 暂不预约 | 进入 `/pages/card/index?userMemberCardId=<ID>` 并定位新发放的用户权益卡 |

导航失败时留在当前页，显示具体原因；不得回首页，也不得进入无卡上下文的普通预约。

## 7. 预约页的会员卡权益模式

### 7.1 初始化状态机

`miniapp/src/pages/order/create.vue` 按以下顺序初始化：

```text
解析 serviceId/serviceCode/memberCardId/source
-> 加载服务详情
-> 按 serviceId 加载可用用户权益卡
-> 验证路由指定的 memberCardId 是否存在且适用
-> 解析可用核销分钟并锁定默认值
-> 加载服务地址和预约时间
-> 携带卡 ID、核销分钟请求价格预览
-> 价格预览成功后允许提交
```

避免服务、会员卡和价格预览并发初始化导致第一次请求仍按现金模式执行。地址、日期、时间或核销分钟变化时重新加载预览，但应取消或忽略过期请求，防止旧请求覆盖新状态。

### 7.2 明确的两种页面模式

| 模式 | 判定 | 页面行为 |
| --- | --- | --- |
| 普通服务权益购买 | 无 `source=member_card`，用户未选卡 | 展示服务商品价、优惠券和提交订单，随后进入支付 |
| 会员卡权益预约 | `source=member_card` 且指定卡校验通过，或用户主动选择可用卡 | 展示用户权益卡、本次核销分钟、应付 0 元，提交后直接进入服务预约详情 |

从会员卡入口进入时：

1. 默认锁定指定用户权益卡，不展示已选中的“不使用会员卡”。
2. 如需切换支付方式，必须通过明确的“改为普通购买”二次操作退出会员卡模式，而不是加载失败自动切换。
3. 卡已到期、暂停、余额不足、不适用或激活截止时间已过时，阻止提交并显示服务端原因。

### 7.3 服务信息展示

会员卡权益模式下不再把 `service.basePrice` 显示为本次应付金额。服务区域改为：

```text
服务名称
服务标准时长/说明
使用会员卡：<卡名>
本次核销：<分钟>
权益余额：预约前可用分钟
```

可以在金额明细中保留服务商品原价用于说明权益抵扣，但必须明确标记为“服务原价”，不能继续显示成“2 小时 99 元”的购买报价。

### 7.4 金额明细

会员卡权益预约的服务端预览结果统一展示：

```text
服务原价          ¥99.00
会员卡权益抵扣   -¥99.00
应付金额           ¥0.00
本次冻结/核销      120 分钟
```

底部操作栏固定显示“应付 ¥0.00”和“提交预约”。普通服务模式继续显示真实应付金额和“提交订单”。

不要使用 `selectedMemberCard ? 0 : payableAmount` 作为最终价格逻辑；页面展示和提交按钮状态以服务端返回的 `pricingMode`、`payableAmount` 和卡校验结果为准。

## 8. 价格预览最小服务端契约

虽然 Day51 是前端流程改造，但正确的 0 元预约需要扩展现有只支持现金/优惠券的价格预览接口。

请求增加：

```text
GET /api/orders/price-preview
serviceId | serviceCode
memberCardId?
memberCardConsumeMinutes?
couponId?
```

会员卡模式下服务端只读校验：

1. 用户权益卡属于当前用户。
2. 卡状态为 `pending_activation` 或 `active`，未暂停、未到期且未超过激活截止时间。
3. 当前服务在卡的结构化适用服务规则内。
4. `memberCardConsumeMinutes` 符合模板版本规则和最小核销分钟。
5. 可用分钟足以覆盖本次冻结。
6. 会员卡权益与优惠券不能同时使用。

响应建议补齐：

```ts
interface PricePreview {
  pricingMode: 'cash' | 'member_card' | 'consultation'
  serviceAmount: number
  discountAmount: number
  memberCardDiscountAmount: number
  payableAmount: number
  memberCardId?: number
  memberCardConsumeMinutes?: number
  memberCardName?: string
  memberCardUsableMinutes?: number
  items: AmountDetailItem[]
}
```

会员卡模式必须由服务端返回 `payableAmount=0`。价格预览不冻结余额、不激活卡、不写账本；实际冻结和首次激活仍只发生在创建服务预约的事务中。

创建订单接口维持 Day49 契约：

```text
POST /api/orders
memberCardId=<用户权益卡ID>
memberCardConsumeMinutes=<服务端预览确认的分钟>
```

创建接口仍需重新执行全部校验，不能信任此前的预览结果。
