# Day48 订单、会员卡与履约链路重构梳理

更新时间：2026-07-14  
范围：订单中心、会员卡购买、用户权益、服务预约、核销、师傅履约与收益、Admin 管理视图  
结论：当前不是“订单只有两种类型”本身有问题，而是购买订单、用户持有的权益卡、服务预约订单和核销记录没有被清晰地建模和呈现。下一轮应以“权益卡生命周期 + 服务履约订单”为主线重构，而不是继续在通用订单列表上叠加字段。

## 1. 统一业务语言

| 名称 | 业务含义 | 是否需要师傅/地址 | 是否可重复使用 |
| --- | --- | --- | --- |
| 会员卡模板 | 营销商品，定义售价、总权益、适用服务、有效期规则 | 否 | 不适用 |
| 会员卡购买订单 | 用户购买模板的支付凭证，支付成功后发放一张用户权益卡 | 否 | 否 |
| 用户会员卡 | 某个用户实际持有的一份权益，记录余额、激活时间、失效时间和生命周期 | 否 | 是 |
| 服务预约订单 | 一次具体服务合同，包含服务内容、用户指定地址、师傅、履约状态和师傅收益 | 是 | 否 |
| 核销单 | 一次服务预约对某张用户会员卡的冻结、实际消耗、释放结果 | 间接 | 否 |

“会员卡购买订单可以多次使用”需要改为：**购买订单只负责支付和发卡；用户会员卡承载可多次使用的权益；每次使用都会生成一个服务预约订单和一条核销记录。**

## 2. 当前实现现状

### 2.1 已有能力

1. `orders.order_type` 已区分 `service_booking`、`consultation`、`member_card_purchase`。
2. 服务预约订单已有地址、派单、师傅履约、订单状态机、服务照片、评价、师傅收入记录。
3. 会员卡模板 `member_cards` 已有售价、权益额度、适用服务、扣减规则和有效期天数。
4. 用户会员卡 `user_member_cards` 已有余额、冻结额度、状态、来源和到期时间。
5. `member_card_records` 已记录发放、冻结、核销、释放、退款撤销和后台调整。
6. 服务预约使用会员卡时，系统已在下单事务中冻结权益；师傅完成服务后按实际时长/次数核销。
7. 用户端有卡包和预约入口；师傅订单详情显示本单会员卡扣减；Admin 已有模板、用户会员卡、流水和两类订单入口。

## 3. 当前链路

### 3.1 购买与发卡

```text
用户/管理员选择会员卡模板
-> 创建 member_card_purchase 订单
-> 支付成功或后台确认线下收款
-> 创建 UserMemberCard
-> 写 grant 流水
-> 购买订单完成
```

当前实现中，发卡时立即将用户卡设为 `active`，并把 `expireAt` 设为“发卡时间 + validityDays”。因此目前没有“未激活”状态，也不是“激活后一年”开始计时。

### 3.2 用卡预约与履约

```text
用户在卡包选择可用卡
-> 创建 service_booking 订单
-> 冻结本次应消耗权益
-> Admin 派单
-> 师傅接单、到达、服务、完工
-> 按实际服务时长/次数核销
-> 如有未使用冻结额度则释放
-> 订单完成，师傅收入按服务预约订单结算
```

这一条履约链路是正确的业务主线：师傅只参与服务预约订单，不参与会员卡购买订单。

## 4. 当前混乱点

### 4.1 一个字段承载两种含义

`orders.member_card_id` 当前在服务预约中保存的是 `UserMemberCard.id`，而会员卡购买订单又通过 `purchaseCardId`、`grantedUserMemberCardId` 等字段保存模板和发卡关系。字段名、数据库关系和 presenter 需要多层猜测才能恢复语义。

后果：

1. Admin 难以从订单列表一眼区分“购买了什么模板”和“本次核销了哪张用户卡”。
2. 师傅端只能从订单快照推断会员卡信息，无法形成标准的履约核销视图。
3. 数据库缺少服务订单到 `UserMemberCard` 的显式外键，关联完整性主要靠应用代码维持。

### 4.2 会员卡生命周期不符合目标业务

当前状态：`active`、`expired`、`used_up`、`disabled`、`refunded`。

问题：

1. 支付成功即 `active`，不存在“未激活”。
2. `expireAt` 由发卡时间计算，不是激活时间计算。
3. 用户查询只读取 `active && expireAt > now`，过期卡会从用户卡包消失；没有完整的历史卡视图。
4. 没有定时任务把到期卡稳定地写成终态，`expired` 状态并非自动生命周期结果。
5. “用完、过期、退款、禁用”被拆成多个技术状态，无法对外统一表达“激活完成”及其原因。

### 4.3 三端视图按表切割，而不是按业务任务组织

| 角色 | 当前入口 | 缺失的连贯视图 |
| --- | --- | --- |
| 用户 | 卡包、购买页、订单详情 | 未激活/进行中/已完成全量权益卡、激活时间、剩余有效期、每张卡的预约与核销历史 |
| 师傅 | 服务订单列表、订单详情 | 本单服务内容、用户指定地址、核销摘要、收益状态应是一张任务卡；不需要也不应查看用户全部卡余额 |
| Admin | 订单、模板、用户会员卡、流水、师傅管理分散 | 从购买订单追到权益卡，再追到服务预约、师傅履约、核销和收益的一条运营链路 |

### 4.4 模板变更与已售权益的边界不清

用户卡持续关联当前 `member_cards` 模板。虽然服务预约时已保存部分扣减规则快照，但用户卡展示、可用服务和后台查询仍大量读取当前模板。模板后续改价、改有效期或改服务规则后，已售卡的权益边界不够明确。

## 5. 目标领域模型

保留统一 `Order` 表作为支付/服务订单的总账，但用明确的一对一领域实体取消字段复用。

```text
MemberCardPlan (会员卡模板，可版本化)
        |
        | 购买
        v
MemberCardPurchase (购买订单扩展，1:1 Order[type=member_card_purchase])
        |
        | 发放
        v
UserMemberCard (用户权益卡，拥有独立生命周期和权益快照)
        |
        | 每次预约生成一条
        v
OrderRedemption (服务预约核销，1:1 Order[type=service_booking])
        |
        +-> MemberCardLedger (不可变权益流水)

Order[type=service_booking]
        +-> OrderAddress
        +-> Staff / OrderAssignment
        +-> StaffIncomeRecord
```

### 5.1 推荐字段边界

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `MemberCardPlan` | `planVersion`、权益规则、`validityDays` | 模板是营销商品；发布后新版本不能改写已售权益 |
| `MemberCardPurchase` | `orderId`、`planId`、`planVersion`、`grantedUserMemberCardId` | 只处理购买、支付、退款、发卡 |
| `UserMemberCard` | `purchaseId`、`planSnapshot`、`status`、`activatedAt`、`expireAt`、`completedAt`、`completedReason`、余额/冻结额度 | 用户拥有的权益实例 |
| `OrderRedemption` | `orderId`、`userMemberCardId`、`state`、`reservedUnits`、`consumedUnits`、`releasedUnits` | 服务预约与权益卡之间唯一、明确的核销关系 |
| `MemberCardLedger` | `userMemberCardId`、`redemptionId`、`eventType`、前后余额、操作方 | 不可变审计账本 |

服务预约不再复用 `orders.member_card_id`。新模型应使用 `OrderRedemption.userMemberCardId` 外键；购买订单的模板关系只由 `MemberCardPurchase.planId` 负责。

## 6. 推荐会员卡状态机

对用户展示三种主状态：

| 用户状态 | 建议代码 | 进入条件 | 可执行动作 |
| --- | --- | --- |
| 未激活 | `pending_activation` | 已支付并发卡，但从未成功预约冻结 | 查看权益、去预约、退款审核 |
| 激活中 | `active` | 首次成功创建带权益冻结的服务预约 | 继续预约、查看剩余时间/次数 |
| 激活完成 | `completed` | 权益用完、到期、退款撤销或后台终止 | 查看历史，不可新预约 |

`completedReason` 必须区分 `used_up`、`expired`、`refunded`、`disabled`，不能再用多个并列主状态让用户和 Admin 自行猜测。

### 6.1 激活时点

推荐规则：**首次服务预约创建成功且权益冻结成功时激活**。在同一事务内写入：

```text
pending_activation
-> 创建服务预约 Order
-> 创建 OrderRedemption(reserved)
-> 冻结权益
-> 写 activatedAt / expireAt = activatedAt + validityDays
-> active
```

这样用户不会因“购买即激活”被动损失有效期，也避免以师傅接单或服务完成作为激活时点带来的不可控延迟。

### 6.2 到期与已冻结订单

到期任务不能简单删除或释放已冻结权益：

1. `expireAt` 到达后立即禁止新预约。
2. 已存在 `reserved` 核销的服务订单允许继续完成或取消。
3. 完成后按已冻结额度核销；取消后释放额度。
4. 没有未结算冻结核销时，将卡置为 `completed + expired`。

这既满足“激活一年后完成”，又不会让已预约用户和师傅产生履约争议。

## 7. 三端目标流程

### 7.1 用户端

```text
购买模板 -> 购买订单支付 -> 未激活权益卡
-> 首次预约 -> 激活中 + 倒计时
-> 多次预约/核销 -> 激活完成（用完或到期）
```

卡包应展示全部卡，而不是只展示当前可用卡：

1. 未激活：权益总额、尚未开始计时、去预约。
2. 激活中：可用/冻结/累计已用、激活日、到期日、剩余天数、预约记录。
3. 激活完成：完成原因、完成时间、历史核销记录。

### 7.2 师傅端

师傅工作台只展示服务预约订单：

```text
服务内容 + 用户指定地址 + 预约时间 + 本单核销规则 + 本单收益
```

师傅可见本单“计划冻结、实际核销、释放额度”和是否需要录入实际时长；不展示用户的其他会员卡、总购买金额或营销信息。会员卡购买订单不进入师傅列表。

### 7.3 Admin 端

Admin 应按运营任务拆成四个互相可跳转的工作区：

| 工作区 | 核心对象 | 必须可追溯 |
| --- | --- | --- |
| 营销配置 | 会员卡模板及版本、服务规则、售价、有效期 | 模板版本影响的新售卡范围 |
| 权益运营 | 用户会员卡 | 购买订单、状态、激活/到期、余额、冻结、终止原因 |
| 订单中心 | 服务预约订单 / 购买订单两个固定视图 | 购买订单 -> 用户卡；服务订单 -> 地址、师傅、核销、收益 |
| 师傅工作台 | 师傅任务和收入 | 每个服务订单的用户、服务内容、地址、核销结果、师傅收益与结算状态 |

建议新增“用户权益时间线”详情页，按时间串起：购买 -> 发卡 -> 激活 -> 每次冻结/核销/释放 -> 完成；从任一订单、用户卡、师傅任务都可跳转到同一时间线。

## 8. 目标接口和查询边界

1. `GET /member-cards/my` 返回全量权益卡，并按三种主状态、剩余天数和完成原因分类；下单页单独请求“可用于该服务的 active 卡”。
2. `GET /staff/orders` 只返回履约订单，并带 `redemptionSummary` 和 `incomeSummary`。
3. `GET /admin/member-card-purchases` 专门管理购买订单，不与服务派单列表混用。
4. `GET /admin/user-member-cards/:id/timeline` 返回购买、激活、核销、终止和关联订单。
5. `GET /admin/staff/:id/fulfillments` 返回师傅服务订单、关联用户、地址、核销和收益；不返回会员卡购买订单。
6. 所有权益余额变动只通过 `OrderRedemption` 和 `MemberCardLedger` 服务写入，禁止页面或通用订单接口直接改余额。

## 9. 重构顺序

### 阶段 A：先确定规则

1. 确认首次预约冻结即激活的规则。
2. 确认到期时已冻结订单的结算规则。
3. 确认退款、后台禁用、补偿赠送是否都归入 `completedReason` 或独立可用性状态。
4. 确认师傅收益只按服务预约订单结算，会员卡购买订单不产生师傅收益。

### 阶段 B：数据模型与迁移

1. 新建 `MemberCardPurchase`、`OrderRedemption`、权益时间线/账本扩展表。
2. 给服务预约明确新增 `userMemberCardId` 外键，不再复用 `orders.member_card_id`。
3. 给用户卡增加购买来源、模板版本快照、激活/完成时间和完成原因。
4. 回填存量：已有 `freeze/consume/release` 流水的卡按最早冻结时间推断已激活；无使用流水的已售卡回填为未激活；历史过期/用完卡回填为完成并标注原因。

### 阶段 C：领域服务

1. 购买支付只负责创建 `pending_activation` 权益卡。
2. 首次冻结事务负责激活和计算到期时间。
3. 核销、取消、退款、过期任务只操作核销实体和不可变账本。
4. 师傅收入继续由服务订单完成事件产生，但关联到核销摘要以便运营查询。

### 阶段 D：三端视图

1. 用户卡包改为三状态权益视图。
2. 师傅任务改为“服务内容、地址、核销、收益”单一履约视图。
3. Admin 拆分购买订单、服务订单、权益卡、权益时间线和师傅履约收入视图。

## 10. 重构前必须避免的做法

1. 不要继续给通用 `orders` 增加更多 `memberCard*` 字段来覆盖不同语义。
2. 不要让师傅端显示会员卡购买订单或用户所有权益余额。
3. 不要只靠查询时 `expireAt > now` 隐藏过期卡；必须有可审计的状态迁移。
4. 不要让模板规则的后续编辑悄悄改变已售权益；已售卡必须保留计划版本快照。
5. 不要让 Admin 在余额页直接人工改数而不写权益账本和原因。

## 11. 需要确认的产品决策

1. 首次预约冻结、师傅接单、服务开始、服务完成四者中，哪个事件是正式激活点？本文推荐“首次预约冻结成功”。
2. 激活后一年到期时，已预约但未完成的订单是否允许按已冻结额度继续服务？本文建议允许结算、不允许新增预约。
3. 未激活卡是否有购买后的最长激活期限？若有，需要增加 `activationDeadline`。
4. `completed` 是否涵盖退款和后台禁用？本文建议主状态统一完成，另用完成原因区分；如需临时停用，单独增加 `availabilityStatus=suspended`。
5. 会员卡是否允许一张卡覆盖多个服务及不同扣减规则？当前系统已经支持，重构时应固化为模板版本快照。
